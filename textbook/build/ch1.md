# Глава 1. Основы безопасности веб-приложений

Глава собрана из тем, которые в рабочей программе МДК.09.03 названы прямо: основные понятия, цели защиты разных объектов, принципы построения безопасных сайтов, классификация опасностей, источники угроз и меры предотвращения, регламенты безопасной разработки, аутентификация и авторизация, методы шифрования, публикация файлов, отказоустойчивость и повышение привилегий как риск. Рядом стоят понятия, нужные для аудита, даже если программа не выделяет их отдельной строкой: граница доверия и поверхность проверки. Они помечены как учебные термины пособия.

## 1.1. Архитектура веб-приложения

Учебный стенд этого практикума устроен так же, как небольшое серверное приложение. Браузер показывает страницу и отправляет запросы. Сервер на Node.js принимает HTTP, Express направляет запрос в функцию маршрута, функция обращается к данным и возвращает ответ. В полном развёртывании между сервером и данными находится PostgreSQL. В среде, где готовилась рукопись, сервер базы не запускался: проверялся текст запроса и отдельный массив значений. Это ограничение студент указывает в отчёте, если воспроизводит только автоматические тесты.

Компоненты, которые нужно уметь назвать:

- клиент — браузер и тот код, который пришёл на страницу;
- сервер приложений — процесс Node.js и маршруты Express;
- хранилище — таблицы заявок и пользователей либо файл зашифрованного хранилища;
- конфигурация — порт, признак HTTPS, ключ хранилища, который не лежит в репозитории;
- журнал — запись события без секрета;
- внешняя граница — всё, что не входит в задание, включая чужие сайты и общую сеть техникума.

Скрытая кнопка в интерфейсе не является защитой. Злоумышленник в учебной модели — это любой клиент, который может послать другой запрос. Поэтому сервер повторяет проверку даже для действия, которого нет в меню.

:::figure Схема компонентов учебного стенда
[Браузер студента]
    |  HTTP-запрос: метод, путь, заголовки, тело
    v
[Express: маршрут и серверные проверки]
    |  только после проверки прав и полей
    v
[Данные: память стенда или параметризованный запрос PostgreSQL]
    |
    v
[Ответ: код состояния, безопасные заголовки, тело без стека и секретов]
:::

## 1.2. Клиент-серверное взаимодействие и HTTP

Клиент и сервер связаны протоколом HTTP. Смысл методов и кодов состояния задаёт RFC 9110. Для занятия достаточно устойчивых правил, а не всего стандарта.

GET запрашивает представление ресурса и не должен быть способом изменить заявку. POST передаёт тело и в стенде создаёт заявку или сессию. Код 200 означает успешный ответ, 201 — создание, 204 — успех без тела, 400 — данные не прошли проверку, 401 — участник не узнан, 403 — участник узнан, но действие запрещено, 404 — объект не найден или его существование скрыто, 413 — тело больше разрешённого размера, 500 — внутренняя ошибка, подробности которой клиенту не отдают.

Заголовок запроса Content-Type говорит, как читать тело. Заголовок ответа X-Content-Type-Options: nosniff запрещает браузеру угадывать тип. Referrer-Policy: no-referrer не добавляет адрес предыдущей страницы к исходящим запросам. Content-Security-Policy ограничивает источники кода и ресурсов. В стенде политика default-src 'self' годится только потому, что страница не загружает внешние сценарии. Переносить её в другое приложение без проверки нельзя.

HTTPS — это HTTP поверх TLS. RFC 8446 описывает TLS версии 1.3. Шифрование канала защищает запрос от прослушивания в сети. Оно не решает, имеет ли студент А право читать заявку студента Б. Эту ошибку проверяют отдельно, в работах по доступу.

В МДК.09.01 программа содержит тему cookie и HTTP-заголовков ответа на материале PHP. В этом пособии те же свойства разбираются на стенде Node.js, потому что задание на рукопись фиксирует этот стек. Подмена PHP в рабочей программе не утверждается.

## 1.3. Основные компоненты серверного приложения

Маршрут связывает метод и путь с функцией. Функция не должна одновременно проверять права, собирать SQL склейкой и писать в журнал пароль. В учебном коде обязанности разделены: access.js решает доступ, validate.js проверяет поля, queries.js возвращает текст команды и значения, errors.js готовит короткий ответ, auditLog.js убирает секреты.

Конфигурация читается из окружения. Ключ хранилища, если он нужен, передаётся в функцию аргументом и не записывается в исходный файл. Режим подробных ошибок для учебной демонстрации стека в маршруты не включён: даже лабораторный сервер отвечает кодом LAB-500.

Зависимости перечислены в package.json. На момент проверки рукописи команда npm install установила Express 4.22.3 при заявленном диапазоне ^4.21.2. Версия меняется со временем. Студент записывает ту версию, которую получил он, и не копирует номер из пособия как вечный факт.

## 1.4. Активы, угрозы, уязвимости и риски

Цель защиты зависит от объекта. Для личного кабинета актив — сведения пользователя и возможность сменить его данные. Для системы заявок актив — текст заявки и статус. Для хранилища документов актив — файл и право его скачать. Для стенда в целом актив — доступность самой лабораторной работы: если процесс остановлен, группа не может учиться.

Опасность в программе классифицируется отдельно от конкретного дефекта. Угроза — возможное нежелательное событие: чтение чужой заявки, изменение статуса без права, появление разметки в комментарии, раскрытие секрета в ошибке, потеря файла из-за непроверенной копии. Уязвимость — дефект, который делает событие выполнимым: нет проверки владельца, данные склеены с SQL, вывод не экранирован, секрет лежит в файле. Риск в пособии оценивается качественно, без формулы, которой нет в программе.

:::table Учебная качественная шкала
Уровень | Когда ставить | Что делать студенту
Критический | Подтверждён доступ к чужим данным или обход основной проверки прав | Остановить дальнейшие пробы, сообщить преподавателю, описать уже увиденное без копий данных
Высокий | Дефект позволяет изменить чужую запись или раскрыть секрет при обычном использовании стенда | Исправить до зачёта работы
Средний | Дефект требует дополнительного условия, но защита ослаблена | Запланировать исправление и повторный тест
Низкий | Влияние небольшое, например отсутствует необязательный заголовок | Исправить в той же работе, если правка короткая
Информационный | Влияние не подтверждено | Записать как гипотезу и указать, какой проверки не хватило
:::

Шкала не заменяет методику организации. Если преподаватель выдаст другую шкалу, в отчёте используют её и ссылаются на лист задания.

Источник угрозы в учебной модели — недоверенный ввод, слишком широкие права процесса, устаревшая или неизвестная зависимость, ошибка конфигурации и потеря носителя с единственной копией. Мера должна совпадать с источником: ввод проверяют и отделяют от команды, права сужают, зависимость сверяют с официальным сообщением, копию восстанавливают в отдельный каталог.

## 1.5. Границы доверия и поверхность проверки

Граница доверия проходит там, где сервер впервые видит данные клиента. До этой границы строка могла быть изменена. После неё сервер либо признаёт её годной, либо отклоняет. Вторая граница — между приложением и базой: в базу должна уйти команда с отдельными значениями, а не строка, собранная из заголовка. Третья — между приложением и журналом: в журнал не попадает пароль.

Поверхность проверки для стенда перечисляют явно:

- POST /api/session — создание учебной сессии по адресу почты из списка, без настоящего пароля;
- DELETE /api/session — завершение сессии;
- GET /api/tickets/:id — чтение заявки;
- POST /api/tickets — создание заявки;
- GET /comments/preview — вывод текста в HTML;
- GET /health — признак, что процесс отвечает.

Всё, чего нет в списке, в этой работе не проверяют. Добавить маршрут «для интереса» на чужой адрес нельзя.

## 1.6. Жизненный цикл безопасной разработки

Регламент в программе — это установленный порядок, а не набор лозунгов. Для учебного проекта достаточен короткий цикл.

1. На проектировании записывают активы, роли и операции.
2. При реализации сервер проверяет роль, владельца и поля; вывод кодируют по контексту; команды к базе параметризуют.
3. При проверке выполняют тесты разрешённого и запрещённого поведения.
4. При исправлении меняют причину, а не только текст сообщения.
5. После исправления повторяют тот же тест и соседний тест штатной функции.
6. В отчёте оставляют область, свидетельства и то, что не смотрели.

NIST SP 800-218 описывает практики безопасной разработки поставщика ПО. Пособие не утверждает, что студенческий стенд соответствует этому документу. Документ используется как внешний ориентир: готовить требования, защищать код, проверять и исправлять дефекты.

Повышение привилегий в программе стоит в одной теме с отказоустойчивостью. В пособии это название риска: процесс или учётная запись не должны получать прав больше, чем нужно для операции. Приёмы получения чужих прав не разбираются. Разбирается обратное действие — назначить файлу и учётной записи минимально нужный доступ и проверить, что приложение всё ещё читает свою конфигурацию.

## 1.7. Назначение аудита безопасности

Аудит отвечает на вопрос, соответствует ли приложение согласованным правилам, а не на вопрос, как далеко можно зайти в обходе. Правила этого практикума такие:

- область записана до начала;
- данные синтетические;
- подтверждённая находка воспроизводится тестом или фрагментом кода;
- гипотеза отделена от факта;
- рекомендация проверяема;
- секреты в отчёт не входят;
- после исправления есть повторная проверка.

Тестирование безопасности уже аудита: оно отвечает, проходит ли конкретный тест. Аудит по регламенту организации шире учебной работы: у него есть заказчик, официальная область, иногда юридические ограничения и утверждённая форма. Пока такого документа нет, итоговая работа студента называется учебным аудитом.

## 1.8. Документирование результатов

Карточка находки содержит идентификатор, название, компонент, условия, наблюдение, ожидаемое поведение, влияние, уровень по шкале, рекомендацию и результат повторной проверки. Шаги наблюдения описывают легальное действие на стенде: открыть файл, запустить тест, сравнить код. Они не описывают воздействие на чужую систему.

Доказательством служит вывод теста, фрагмент исправленного кода и кратко описанный ответ сервера без заголовков Cookie и Authorization. Снимок экрана допустим, если на нём нет секрета и чужих персональных данных.

## 1.9. Шифрование, хеширование и подпись

Программа объединяет методы шифрования с темами SQL-инъекций и XSS. Это разные задачи, и смешивать их в одном механизме нельзя.

Хеширование пароля необратимо для практического подбора на занятии: в стенде используется scrypt из библиотеки node:crypto, соль хранится вместе с результатом, исходный пароль в строке результата не содержится. Сравнение выполняется функцией timingSafeEqual. Это учебный приём стандартной библиотеки Node.js, а не утверждение о сертификации алгоритма.

Шифрование хранилища обратимо при наличии ключа. Стенд использует AES-256-GCM: вместе с шифртекстом сохраняются случайный вектор инициализации и тег подлинности. Ключ длиной 32 байта передаётся снаружи. Файл с шифртекстом без ключа для занятия бесполезен, но ключ, положенный рядом, отменяет смысл хранилища.

Электронная подпись подтверждает, что документ не изменён с момента подписи и что подпись создана парным закрытым ключом. В практической работе 14 пара ключей Ed25519 создаётся в памяти процесса. Это не сертификат удостоверяющего центра и не квалифицированная подпись. TLS-сертификат сервера решает другую задачу: браузер проверяет имя сервера и шифрует канал. Называть самоподписанный сертификат localhost электронной подписью документа нельзя.

## 1.10. Доступность без испытания отказом в обслуживании

Программа содержит практические занятия «Тестирование на устойчивость к атакам отказа в обслуживании» и такой же пункт производственной практики. Создавать нагрузку, подбирать число соединений и пользоваться инструментами отказа в обслуживании это пособие не учит. Для компетенции достаточно понять свойство доступности и защитную границу.

Стенд ограничивает тело JSON шестнадцатью килобайтами средствами Express и отдельно проверяет функцию checkBodyLimit. Слишком большой учебный размер получает код LAB-413. Такой тест не создаёт поток запросов и не измеряет, при какой нагрузке процесс упадёт. Если организации действительно нужно испытание устойчивости, его проводят по отдельному регламенту, на выделенной копии, с пределом интенсивности и с правом остановить пробу. Студент в отчёте пишет, что эта часть не выполнялась.

## 1.11. Публикация файлов и технологическая независимость

Публикация изображений и файлов в программе — отдельная тема. Файл пользователя опасен тем, что имя может содержать путь, тип может оказаться исполняемым документом, а размер может занять диск. Учебное правило: расширение только из списка, имя на диске назначает сервер, путь не выходит из каталога хранилища, файл не кладут в каталог, откуда сервер выполняет код.

Технологическая независимость в этом пособии означает другое. Студент может прочитать стандарт HTTP, документацию Node.js, Express и PostgreSQL, запустить стенд локально, повторить тест и заменить инструмент просмотра заголовков на любой браузер с инструментами разработчика. Пособие не утверждает, что конкретный свободный инструмент является отечественным, сертифицированным или обязательным. Платные сервисы для выполнения работ не требуются. npm нужен для установки Express; если сеть аудитории закрыта, преподаватель раздаёт уже установленный каталог node_modules и фиксирует это в журнале.

Повторная проверка исправления устроена одинаково для всех работ.

:::figure Жизненный цикл исправления в учебном аудите
Наблюдение на стенде
    -> карточка: факт, влияние, граница
    -> правка причины в коде
    -> тот же тест
    -> тест штатного сценария
    -> отметка в листе повторной проверки
:::

Если повторный тест не проходит, находку не закрывают. Если проходит только штатный сценарий, но не запрещённый, находку тоже не закрывают.
