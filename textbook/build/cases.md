# Глава 4. Кейсы и задания для самостоятельной работы

Кейсы не требуют доступа к чужим системам. Исходные данные синтетические. Если студент не может показать файл или тест, вывод остаётся гипотезой. Базовый кейс оценивается из 10 баллов по таблице внутри кейса. Средний и повышенный добавляют один вопрос обсуждения, но не меняют шкалу, если преподаватель не сказал иначе.

## Кейс 1. Личный кабинет и чужая запись

Уровень: базовый.

Ситуация. В учебном личном кабинете страница профиля открывается по адресу с идентификатором. Студент А меняет идентификатор на идентификатор студента Б в своём локальном стенде и видит фамилию «Студент Б». Сервер не сравнивает идентификатор сессии с владельцем записи.

Исходные данные. Две записи: user-01 «Студент А» и user-02 «Студент Б». Маршрут чтения есть только на локальном приложении. Реальных фамилий нет.

Постановка задачи. Назовите класс проблемы, укажите, какая серверная проверка отсутствует, составьте один разрешённый тест на своём стенде и критерий исправления.

Ограничения. Нельзя перебирать идентификаторы за пределами двух записей и нельзя повторять опыт на адресе, отличном от 127.0.0.1.

Ожидаемый результат. Текст на одну-две страницы: название CWE-639 или словесное описание подмены ключа, тест «сессия А не читает запись Б», признак закрытия — код отказа и отсутствие полей записи Б в теле.

Критерии. Верно названа причина — 0–3. Тест выполним на стенде и не шире двух записей — 0–3. Критерий исправления наблюдаем — 0–2. Нет секретов и чужих адресов — 0–2.

Вопросы для обсуждения. Почему скрытый адрес профиля не заменяет проверку? Чем этот случай отличается от отсутствия входа вообще?

## Кейс 2. Система заявок и статус

Уровень: базовый.

Ситуация. Оператор видит заявки только своей смены, но клиент может прислать статус archived, которого нет в правилах. Сервер сохраняет строку как есть. В интерфейсе такого пункта нет.

Исходные данные. Допустимые статусы: new, open, closed. Роли: автор заявки и оператор своей заявки. Поле status приходит в JSON.

Постановка задачи. Разделите дефект валидации и дефект авторизации, если для смены статуса ещё и не проверяется роль. Предложите два отдельных теста.

Ограничения. Не используйте реальные тексты заявок техникума.

Ожидаемый результат. Две карточки или одна карточка с двумя независимыми причинами. Для статуса признак закрытия — ошибка поля. Для роли признак закрытия — отказ, даже если статус входит в список.

Критерии. Две причины не смешаны — 0–4. Оба признака закрытия конкретны — 0–4. Ограничение данных соблюдено — 0–2.

Вопросы для обсуждения. Может ли исправление списка статусов оставить дыру в правах? Почему?

## Кейс 3. Интернет-магазин и отзыв

Уровень: средний.

Ситуация. Отзыв о товаре сохраняется и выводится на странице товара как HTML. Правило вывода не записано. Товар и отзыв — синтетические, оплата не выполняется.

Исходные данные. Товар «Учебный блокнот», отзыв содержит угловые скобки, как в тесте экранирования. Платёжных данных нет.

Постановка задачи. Определите контекст вывода, предложите функцию текстового экранирования и регрессионный тест. Отдельно напишите, что проверка «отзыв не длиннее 500 знаков» не заменяет экранирование.

Ограничения. Не составлять строку, которая должна выполниться в браузере. Не подключать платёжный сервис.

Ожидаемый результат. Контекст назван текстовым узлом, указана escapeHtml или равноценная замена, тест сравнивает наличие сущностей, а не внешний вид «на глаз».

Критерии. Контекст указан — 0–3. Тест проверяет данные, а не исполнение — 0–3. Валидация длины отделена — 0–2. Нет платёжных данных — 0–2.

Вопросы для обсуждения. Что изменится, если отзыв вставляют в атрибут, а не в текст? Почему одна и та же функция может не подойти?

## Кейс 4. REST API панели приёма документов

Уровень: средний.

Ситуация. API выдаёт карточку документа по идентификатору. Ошибка базы с текстом запроса и путём сервера попадает клиенту, если идентификатор не строка. Параллельно автор карточки не проверяется.

Исходные данные. Два документа doc-01 и doc-02 разных владельцев. Тело ошибки в дефектном варианте содержит слова SELECT и путь /home/student. В исправленном варианте клиент видит только код LAB-500.

Постановка задачи. Оформите две находки: состав ошибки и доступ к объекту. Предложите порядок исправления и объясните, какую закрывать наблюдаемым тестом первой, если время одно.

Ограничения. Не повторять текст настоящего запроса к боевой базе. Слова SELECT и путь в исходных данных уже учебные, их можно цитировать как пример плохого ответа.

Ожидаемый результат. Две записи реестра. Приоритет обоснован: раскрытие внутреннего запроса и чужой документ сравниваются по последствию для данных, а не по тому, «что проще починить».

Критерии. Обе находки разделены — 0–3. Приоритет объяснён последствием — 0–3. Признаки закрытия разные — 0–2. Чужая база не затронута — 0–2.

Вопросы для обсуждения. Почему код 500 с коротким текстом всё ещё требует отдельной проверки прав?

## Кейс 5. Панель администратора и сессия

Уровень: средний.

Ситуация. После выхода администратора учебный браузер продолжает показывать кнопку «журналы», потому что страница не обновилась. Повторный запрос к API со старой сессией всё ещё успешен. Значение cookie в условии не приводится.

Исходные данные. Роль admin, действие «закрыть сессию», затем GET защищённого маршрута.

Постановка задачи. Отделите дефект интерфейса от дефекта сервера. Составьте таблицу состояний, как в лабораторной работе 4. Предложите признак исправления сервера.

Ограничения. Не копировать идентификатор сессии. Не проверять панель реального сайта техникума.

Ожидаемый результат. Вывод: скрытие кнопки не является исправлением. Исправление — сервер забывает сессию, следующий запрос получает отказ.

Критерии. Два слоя разделены — 0–4. Таблица состояний полна — 0–3. Секрет не раскрыт — 0–3.

Вопросы для обсуждения. Что добавить к признаку, если идентификатор сессии был предсказуемым, как в учебном стенде?

## Кейс 6. Сервис хранения документов

Уровень: повышенный.

Ситуация. Сервис сохраняет файл под исходным именем клиента и кладёт его в каталог, откуда раздаётся и статика. Расширение не проверяется. Размер не ограничен.

Исходные данные. Каталог storage рядом с приложением, предложенные имена: отчёт.txt, page.html, имя с переходом к родительскому каталогу в виде текстового описания, без выполнения.

Постановка задачи. Составьте правила из практической работы 15 и добавьте предел размера из работы 16. Опишите, как проверить правила тестами функций, не поднимая приём файлов в открытую сеть.

Ограничения. Не загружать исполняемое содержимое. Не менять права вне временного каталога.

Ожидаемый результат. Три правила: список расширений, имя от сервера, каталог вне зоны исполнения, плюс предел размера. Для каждого — наблюдаемый признак.

Критерии. Четыре правила на месте — 0–4. Признаки наблюдаемы — 0–4. Нет загрузки опасного содержимого — 0–2.

Вопросы для обсуждения. Почему верное расширение не доказывает содержимое? Какую проверку начала файла вы предложите отдельно?

## Кейс 7. Секрет в учебном репозитории

Уровень: повышенный.

Ситуация. В файле конфигурации практиканта лежит строка, похожая на ключ от учебного стенда. Файл уже попал в историю версий на локальном компьютере. Внешний сервис ключ не принимал: это генерация для занятия.

Исходные данные. Путь config/lab.env и пометка «значение не переписывать в отчёт».

Постановка задачи. Опишите порядок: остановить публикацию, сообщить преподавателю, оценить, где файл успел оказаться, заменить ключ новым, не проверяя старый ключ на чужих адресах, исключить файл из дальнейших копий.

Ограничения. Не вставлять значение. Не искать его в интернете.

Ожидаемый результат. Пошаговый порядок из пяти действий и фраза, почему удаление файла без замены ключа недостаточно, если ключ уже куда-то скопирован внутри группы.

Критерии. Пять действий по существу — 0–4. Отказ от публикации значения — 0–3. Объяснена замена, а не только удаление — 0–3.

Вопросы для обсуждения. Что изменить в проверке перед размещением, чтобы такой файл не попал в следующую копию?
